# Artifact Shapes for Representing Ownership, Forbidden Surfaces, and Freeze Boundaries in Concurrent Software Work

Concurrent software development introduces fundamental coordination challenges around which developer controls which code artifacts (ownership), which areas are at risk of conflicting edits (forbidden surfaces), and which regions should remain stable (freeze boundaries). The visualization literature has converged on a set of shape-based metaphors to represent these three concepts. This answer synthesizes findings from workspace awareness tools, software visualization systems, and ownership analysis approaches.


* * *


## 1\. Ownership: Stacked Cylinders, Colored Lines, and Hierarchical Boxes

**Ownership** answers the question: *who is responsible for or has contributed to a given software artifact?* The most effective shapes for representing ownership leverage color mapping and layered geometry.

**Stacked cylinders (3D city metaphor).** TeamWATCH visualizes each file as a stack of colored cylinders (a "building"), where each cylinder represents a revision and its color encodes the developer who authored that revision \[1 \]  . The height of the stack conveys the total number of revisions, and the dominant color at the top of the stack indicates the most recent owner. This shape metaphor leverages the built-in human ability to quickly assess a cityscape: tall buildings with a single dominant color signal concentrated ownership, while multicolored stacks signal shared/team ownership \[1 \] .

**Colored in-line bars (time-encoded ownership).** For per-line ownership within source code, Beck et al. demonstrated that thin colored horizontal bars positioned beneath each line of code can encode fractional ownership over the file's revision history \[2 \]  . The horizontal axis represents time, and colored segments within each bar show which developer contributed which portion. Crucially, this shape encodes *uncertainty* via saturation: when ownership is evenly split among multiple developers, the bar segment becomes desaturated (gray), signaling that *no single developer clearly owns the line* \[2 \] .

**Rectangular treemap cells (software maps).** Software cartography approaches represent files and modules as nested rectangular cells in treemaps, with color mapped to ownership metrics (e.g., number of commits per author) and area mapped to code size \[3  ,4 \]  . Position in the 2D layout reflects vocabulary similarity, enabling developers to identify clusters of semantically related artifacts and their respective owners \[3 \] .

**Color-coded boxes in package explorers.** Palantir augments the standard IDE package explorer with small colored triangular overlays and percentage annotations beside file names, indicating who is actively modifying which artifact and the severity of ongoing changes \[5 \] .

**Hierarchical matrices with dominator trees.** For deep *object-level* ownership within running programs, dynamic analysis of write control graphs produces ownership trees that show which objects dominate (own) which others \[6 \]  . These are rendered as interactive hierarchical matrices, where dots represent cross-hierarchy edges (read, write, or creation) that violate encapsulation boundaries, drawing the programmer's attention to unexpected sharing \[6 \] .


* * *


## 2\. Forbidden Surfaces: Animated Signs, Triangular Icons, and Shaking Geometry

**Forbidden surfaces** refer to regions of the codebase where concurrent modifications are occurring or are likely to produce conflicts. These are "hot zones" that developers should avoid editing simultaneously. Effective shapes for forbidden surfaces are attention-grabbing, dynamic, and intuitively convey *danger* or *contention*.

**Shaking buildings (3D animated alerts).** TeamWATCH uses a striking dynamic shape: when two or more developers modify the same file concurrently, the corresponding 3D building (cylinder stack) begins to *shake* , providing an unmistakable visual warning that this artifact is a conflict zone \[1 \] . This shape leverages natural human sensitivity to motion and vibration as signals of instability.

**Smoke emissions (active-editing indicators).** In the same 3D city metaphor, when a developer begins editing a file, colored "smoke" rises from the corresponding building—the color identifies the developer \[1 \] . This creates a visible plume over forbidden zones, enabling team members to spot which artifacts are currently "hot" from across the visualization.

**Colored triangular overlays (severity-coded icons).** Palantir represents direct conflicts with a **blue triangle** in the upper-left corner of the artifact icon, whose size and color intensity grow with the *severity* (percentage of code changed) of the parallel modification \[5 \]  . Indirect conflicts—where a change to one artifact's public interface breaks dependent artifacts in another workspace—are marked with a **red triangle** in the upper-right corner \[5 \]  . These shape attributes (position, color, size) are mapped to different conflict dimensions: location tells the conflict *type* , size tells the *magnitude* , and color saturation tells the *urgency*.

**Textual severity annotations.** Palantir supplements geometric icons with compact textual annotations: `[S:24]` indicates 24% of the file has been changed, and `[I]` indicates an indirect conflict is present \[5 \] . This hybrid shape–text encoding allows developers to quickly assess whether a forbidden surface requires immediate attention.

**Building glow and highlighting.** When a developer hovers over or clicks on a building in TeamWATCH, the building glows, allowing users to highlight and track a particular artifact of interest \[1 \] . This interactive shape manipulation helps developers tag potential conflict zones for monitoring.

**Height-based reference surfaces.** In 2.5D software maps, a horizontal reference plane can be positioned at a configurable height to visually filter artifacts that exceed a threshold metric value—effectively creating a "cutoff surface" that separates problematic artifacts from acceptable ones \[4 \] .

## 3\. Freeze Boundaries: Dormancy Positioning, Gray Transitions, and Radial Separation

**Freeze boundaries** demarcate code regions that are considered stable/frozen and should not be modified. These are artifacts whose changes have been completed, have been committed, or are explicitly locked. Effective shapes for freeze boundaries visually communicate *stability, age, and separation*.

**Positional drift to rear (3D workspace activity viewer).** In the Workspace Activity Viewer, artifact cylinder stacks that have not been recently modified gradually drift **toward the rear** of the 3D scene as they become dormant \[7 \]  . This spatial positioning—front for active/hot artifacts, back for cold/frozen ones—creates a natural freeze boundary: artifacts that have moved to the back are effectively "frozen" and should not be targeted for new changes. The view can be rotated to an overhead perspective, providing a shaded-relief map where dark cylinders near the base are recent and light cylinders farther back are aged \[7 \] .

**Grayscale desaturation and size reduction (working-set visualization).** In the working-set evolution visualizer, program entities that have not been interacted with recently are aged out of the "current working set" into a radially arranged "past working set" \[8 \]  . Nodes in the past working set are placed on an equidistant circular layout outside the central force-directed graph, with their size reduced and color shifted toward lighter gray tones \[8 \] . This visual separation creates a clear freeze boundary between active entities (central, large, dark) and frozen entities (peripheral, small, light).

**Transparency for deleted/removed components.** In software map visualizations, transparency can be applied as a visual variable to encode node state—artifacts that are deleted, removed, or planned (but not yet implemented) can be rendered semi-transparent \[4 \] . This creates a visual freeze boundary: fully opaque elements are live and modifiable, while transparent elements are frozen or historical.

**Circular/radial layout separation.** The working-set visualizer places frozen ("past") entities on a radial layout at a fixed distance from the center, while active ("current") entities occupy the inner force-directed layout \[8 \] . This geometric separation—circle vs. center—creates an unmistakable spatial freeze boundary around the perimeter.

**Sketchiness as uncertainty encoding.** When freeze boundaries are uncertain or imprecise (e.g., a module is "mostly frozen" but could still change), software maps can use **sketchiness** —pencil-like outlines and hatching on surfaces—as a visual variable to encode uncertainty, imprecision, or vagueness \[4  ,9 \] . A smooth, clean outline signals a definite freeze boundary, while a sketchy, hatched outline signals an approximate one.

**Contour nesting for aggregation depth.** When visualizing frozen aggregates (e.g., stable module groups), multiple nesting-level contours—concentric outlines that indicate the depth of the aggregated sub-tree—can convey how many hierarchical levels of frozen content lie beneath a surface \[4 \] .

**Texture-based freeze indicators.** Different texture patterns (e.g., cross-hatching, solid fill) can be applied to surface material properties such as metalness or roughness to indicate deterioration, stagnation, or "rustiness" of frozen artifacts \[4 \] . A "rusty" texture visually communicates that an artifact has been untouched for too long and may need maintenance to remain viable.

## Summary: Mapping Shapes to Coordination Concepts

| Concept | Best Shapes | Key Visual Variables | Example Tools |
| --- | --- | --- | --- |
| **Ownership** | Stacked cylinders, colored in-line bars, treemap cells, hierarchical matrices | Color (developer), height (contribution count), saturation (confidence) | TeamWATCH \[1 \] , Fractional Ownership View \[2 \] , Software Maps \[3 \] , Ownership Trees \[6 \] |
| **Forbidden Surfaces** | Shaking buildings, colored triangles, smoke plumes, triangular icons | Motion (alert), position (type), size (severity), color saturation (urgency) | TeamWATCH \[1 \] , Palantir \[5 \] |
| **Freeze Boundaries** | Rear-positioned stacks, gray desaturated nodes, radial/outward separation, transparent elements, sketchy contours | Spatial position (active vs. dormant), transparency (stability), texture (staleness) | Workspace Activity Viewer \[7 \] , Working-Set Viz \[8 \] , Software Maps \[4 \] |

The overarching design principle is that **multiple shape attributes must be combined** —color, size, position, motion, transparency, texture, and contour—to simultaneously convey these three coordination dimensions without overloading any single visual channel \[9  ,10 \]  . Shape attributes such as curvature, terminator style, edge type, and corner style provide additional degrees of freedom for encoding nuanced coordination states \[9 \]  . The most successful tools embed these shapes directly into the developer's IDE (in-situ visualization) or provide ambient overview displays, enabling developers to maintain workspace awareness without disrupting their primary coding workflow \[1  ,5  ,11 \] .
