# B03 proposal: Lane, World association, and accepted-work binding

**Status:** Draft for owner-contract review, updated 2026-10-21. Not an accepted API, canonical-owner replacement, implementation dispatch, or runtime-readiness claim.
**Purpose:** Make the confirmed multi-World Lane model precise enough for Collider to display and control one exact accepted task without guessing its execution destination.
**Companion:** [B01–B05 handoff](collider-b01-b05-handoff.md), including evidence pins, shared boundaries, and remaining decisions.
**Intent source:** [Core architecture dossier](../../../SUBSTRATE_CORE_ARCHITECTURE_SESSION_DECISIONS_2026-09-20.md), especially SCA-02–05 and SCA-07–12. The dossier retains confirmed intent; this file proposes its contract expression.

**Planning checkpoint, 2026-09-21:** B03's target behavior is ready for review as part of the [bounded B01–B05 planning handoff](collider-b01-b05-handoff.md#91-planning-handoff-disposition). Collider selects an existing owner-backed association, retains the exact returned references, and displays historical binding separately from current association. It does not create/move/promote Worlds through this bounded consumer surface. Concrete storage/fencing/custody mechanisms and runtime proof remain implementation gates, not prerequisites to planning against these semantics. This checkpoint does not approve the new owner contract or declare it callable.

## 1. Scope and authority

The narrow consumer needs Lane/World selection by an authenticated caller, authorization for the requested operation, a validated association, immutable execution provenance, and an authorized read of that provenance. It does not need a merge engine, automatic routing, remote backing, or an always-running lane orchestrator.

**Initial same-host opening:** Collider opens the Substrate Workspace through the proposed
[B01-B03-P1 native adapter](../../../llm-last-mile/runtime-refactor/slices/tasks/b01-b03-authenticated-preflight.md#substrate-workspace-open-load-and-initialize).
Existing valid `.substrate` state loads current known config/policy/Lanes/destinations without
Connect/enrollment/pairing/issuer approval. Genuinely absent state offers one initial settings
approval through Substrate; invalid/incomplete/disabled/incompatible state is diagnosed/refused,
not repaired/regranted or converted to default/parent state. A folder is discovery input, not
Workspace identity or execution permission. Existing Lane/association reads must be genuine owner
state; unsupported source exposure stays explicit. Initialization and read-only preflight have
distinct effects and proof; opening creates no association reservation or task acceptance.

This proposal does not add fields to an existing V1 record. Operation labels and semantic field lists below are design vocabulary, not callable APIs or selected serialization. Existing strict decoding, reference validation, and owner boundaries remain controlling until explicitly amended.

The current [authority map](../../../llm-last-mile/runtime-refactor/architecture/authority-map.md) assigns session identity and session-to-World binding authority to HSA, physical realization to the runtime/backend, acceptance to the Receipt Registry, observation/terminal truth to the Supervisor, and worker lifecycle to RetainedWorkerRuntime. None becomes a second Lane scheduler through this proposal.

**Recommended ownership:** establish a Workspace-scoped Lane-association authority in the shell/agent-runtime authority layer, reusing trusted persistence capabilities rather than creating another service or scheduler. It owns Lane identity, current World association, association history, and association-admission reservations. HSA retains session identity/posture/continuity; backend/runtime owners retain physical World custody. The 2026-10-21 target module/transaction interfaces are selected in §§4.7–4.9 for review; versioned schemas/implementation and real owner support remain later proof obligations. This is a new logical responsibility, not a claim that HSA already owns multi-World Lane state. The source-backed recommendation and required changes are below.

## 3. Proposed identity and reference model

Keep these meanings distinct even if an implementation can store some together:

| Identity/reference              | Meaning and owner                                                                                                                                                      |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace reference             | Authorized Workspace identity; not a directory string supplied as authority.                                                                                           |
| Lane reference                  | Stable identity within its Workspace. A display name is not an authorization token.                                                                                    |
| World realization reference     | Exact backend World identity and generation/realization discriminator validated by existing World owners. Do not repurpose generation to mean a sibling World or Lane. |
| Association reference/revision  | Owner-issued evidence that this World is associated with this Lane at a specified revision. Changes create history, not retroactive relabeling.                        |
| Work/acceptance reference       | Exact accepted task/turn identity from the existing acceptance owner; not a Lane, worker, provider session, or UI segment ID.                                          |
| Orchestration/worker references | Coordinator and worker identities, separately authorized for their roles. Their lifetime does not define Lane lifetime.                                                |
| Configuration provenance        | References to baseline, explicit overrides, effective desired configuration, and applied environment evidence; not one interchangeable hash or permission grant.       |

References are opaque and owner-validated. Reuse existing exact ref and store conventions where applicable; do not expose private leases, credentials, resume handles, or internal capabilities to Collider. Whether a World can be unassociated before admission remains outside this proposal's selected path, which requires an existing associated World.

### 3.1 Review candidate: separate membership, association, and acceptance revisions

Use an owner-qualified Workspace/Lane reference and an exact backend World reference. A bare `world_id` is insufficient outside its owning scope; preserve the existing store/backend/world/generation qualification wherever the owner requires it. Restoring or copying storage must not silently mint a second authority for the same references.

Recommended semantic shapes (not serialized records or new public type names):

```text
DestinationExpectation = {
  workspace_ref, lane_ref, exact_world_ref, expected_world_association_revision
}
AcceptedBinding = {
  exact_acceptance_ref, destination_at_acceptance
}
```

`destination_at_acceptance` contains the same four identity/revision meanings as `DestinationExpectation`, validated by owners rather than copied from the client. `exact_acceptance_ref` retains the existing authority-store/acceptance-record/revision qualification; the authenticated join resolves the exact task/run, request, session, and caller. Names here do not replace the existing ref schemas.

- **Lane membership revision** identifies the association-list cut; adding an unrelated sibling World may change it.
- **World association revision** identifies this World's current Lane association. A move A→B→A must not make the old A selector valid again. Reject stale revisions even when names/IDs appear unchanged. Numeric encoding and revision allocation remain open.
- **Acceptance/observation revisions** belong to the existing work owners, not either association revision. A new observation or renamed Lane does not rewrite `AcceptedBinding`.

Bind admission to the selected World's association revision, not a Lane-wide display revision. This avoids rejecting unrelated work merely because another World joined the Lane. Separately validate current policy/configuration requirements; an unchanged association revision is not proof that they remain valid. List-cursor invalidation and admission validity are different decisions.

## 4. Proposed operation semantics

### 4.1 Read a Lane and its associated Worlds

**Input:** authenticated caller, Workspace/Lane reference, optional continuation cursor.
**Success:** Lane-owned facts at an identified association revision; authorized associated World references; separately sourced observations and their freshness/completeness. Lists use owner-scoped cursors and an explicit end/continuation indicator.
**Failure:** denied, unknown target, stale cursor, unavailable owner, unsupported operation/version, or invalid reference. Unauthorized callers must not receive hidden World identities through errors or lists.

This read is not a global Workspace snapshot. A coherent association listing does not imply all worker, diff, policy, or readiness projections share one atomic cut. Partial observations remain explicitly partial.

### 4.2 Validate a concrete execution destination

**Input:** authenticated caller/delegation, Workspace, Lane, exact World realization, expected association revision, requested operation, and relevant configuration/context expectations.
**Checks:** same Workspace; current exact association; authorized caller and operation; matching realization; current applicable policy; required capability/readiness; configuration/context preconditions.
**Success:** owner-validated binding evidence for the submission boundary. It is not acceptance, a permanent authorization grant, or permission to skip launch-time validation.

For the first proof, require an explicit existing World selection. A Lane-only request with several Worlds is not executable work until an authorized coordinator selects a concrete destination. Reject absent/ambiguous selection rather than choose an arbitrary World or create one silently. An orchestration message may target a Lane to request planning; it is not yet B01 World-work acceptance.

Proposed public failure meanings include missing destination, association changed, wrong Workspace/Lane, realization mismatch, policy denied, unsupported capability, readiness unavailable, and owner unavailable. Exact serialized variants and privacy-preserving mappings remain owner design work.

### 4.3 Bind accepted work without a race

1. Resolve the concrete destination and capture its association revision before a possible launch effect.
2. The association authority and dispatch/admission owners establish a revision-bound reservation or equivalent serialized protocol. A check followed by an unguarded launch is insufficient.
3. Keep the selected association stable through runtime submission and uncertain acknowledgement. A transition cannot evade an in-flight admission merely because it has not produced a receipt yet.
4. Only existing runtime acknowledgement and acceptance owners can establish accepted work. Bind its immutable provenance to the exact Workspace, Lane, World realization, association revision, and applicable accepted policy/configuration references.
5. Publish a consumer acceptance result only after its required receipt, supervision, policy, and binding joins are durable and recoverable. If reporting fails after runtime acceptance, reconcile the same work; do not launch another task.

The 2026-10-21 target protocol in §§4.7–4.9 selects per-owner serialization, authenticated forward joins, service fencing and positive release evidence. Its storage/carrier schema implementation remains future work. Unknown submission is not safe evidence for releasing state custody or changing destination.

**Preserve acceptance ownership:** B03 evidence neither manufactures acceptance nor changes the immutable acceptance owner's meaning. The receipt owner must choose an explicit versioned carrier or authenticated linked projection; never append unrecognized fields to a frozen V1 schema.

### 4.4 Read historical binding

Read accepted binding by exact work/receipt reference under current caller authorization. Return the association at execution acceptance, separately from any current World association. If World W moves from Lane A to Lane B, work accepted in A remains attributed to A. Authorized views may show the move separately; they must not relabel old work as executed in B.

Historical provenance does not grant present action authority. Cancellation/inspection continues through exact accepted-work owners; never substitute the World's current Lane or newest run for the original target. If a transition makes a live route unavailable, expose that condition rather than inventing terminality or redirecting cancellation to different work.

### 4.5 Proposed receipt composition and the HSA bridge

**Recommended carrier:** return a versioned consumer composition containing the existing authenticated receipt projection plus an authenticated `AcceptedBinding` projection. Keep the B03 relationship with its Workspace association owner and join it to the existing exact B1 acceptance reference; do not add Lane fields to frozen receipt V1, copy acceptance into a second registry, or expose the private E2-RM witness. The concrete proposed storage/transaction/recovery responsibility is specified in §§4.7–4.9; its versioned implementation is not present.

The binding may be prepared against a proposed acceptance ID before launch, but it is not an accepted binding until joined to actual B1 acceptance. Runtime acceptance can precede completion of this consumer composition. If any required join is missing or conflicting, return the recoverable B01 request disposition, not a fabricated complete receipt or a refusal implying nothing launched. [B01's outcome table](collider-b01-b05-handoff.md#31-request-admission-and-consumer-acceptance-are-separate) governs that distinction. A conflicting durable join needs owner recovery; it is never repaired by reading the World's current Lane.

**Source-backed disposition:** current exact-session dispatch is reusable only when its canonical caller and bound World already match the request. It cannot directly express a Workspace orchestrator dispatching into a different selected World: the source resolver unconditionally enforces caller/session/World equality before launch. The additional physical session-ownership constraint also matters for retained/member execution. These are specific extension points, not evidence that every HSA schema must change or that singular session binding should become a list. §7 records the inspected paths.

### 4.6 Recommended model: authorized selection, not session rebinding

**2026-10-21 target extension:** keep initiating principal, HSA execution actor, Workspace/Lane association and backend custody distinct. The proposed concrete interfaces in §4.8 implement this responsibility split; they are not current exports, component-owner signoff or runtime readiness. [B01 §§3.2–3.4](collider-b01-b05-handoff.md#32-immutable-request-identity-and-the-admission-boundary) supplies authenticated ingress, complete semantic equality, original B04 material, read/privacy/retention and the real-profile proof manifest.

1. Ingress authenticates host peer plus enrolled client/principal. Workspace authority resolves trusted enrollment/root/store and an exact operation/resource delegation; HSA resolves canonical session/caller/backend/World and current policy facts. A human cannot supply an invented orchestrator participant. A valid stored record or typed proof alone grants no operation permission.
2. Workspace association authority validates `(workspace, lane, world, world_generation, association_revision)` and reserves that **World's** revision for the original correlation. Lane names, session IDs, paths and branch names are not that authority. A→B→A increments revision; unrelated sibling membership/name changes do not invalidate the selected World's unchanged revision.
3. Runtime/backend authority positively validates existing exact physical custody. The first route uses an eligible existing session/caller whose World already matches and whose real backend owner/generation agrees; mismatch refuses without adoption/rebinding. The acting coordinator is not automatically the physical owner. General selected-World dispatch needs a separately implemented composite resolver/custody grant and is outside the first implementation profile.
4. Policy owners decide current initiator/delegation/operation/destination restrictions; E1 materializes effective policy, E2 retains its immutable accepted inputs. Handbook supplies applicable source/disclosure/current-use evidence for original retained material. Association reservation is no permission freeze. Effect admission and later delivery/current-use guards remain separate.

A Lane orchestrator's authorization is bounded to its Lane; Workspace orchestration remains limited to its actual grants. Direct intervention keeps its real initiator and visible causation. Cross-coordinator control checks present action authority against original work/cap identity; it cannot rewrite its creator. No plural World field or temporary HSA rebind is selected. Host placement without an executable exact World grant remains non-executable. Durable multi-World Lanes remain the product model; this exact-session proof does not shrink them to sessions or one World.

The owner-produced internal admission witness joins canonical actor/delegation, original request/seal, destination reservation, policy and custody revisions. It authenticates validated owner decisions and is usable only through the consume/fence handshake below; it is not a reusable bearer permit or a new source of authority. New carriers are versioned explicitly rather than adding unrecognized fields to frozen V1/V2 schemas.

### 4.7 Association/admission consistency and recovery

**Selected storage/protocol:** proposed `ConsumerAdmissionStorage` binds trusted StateStore/HSA descriptor-relative persistence to one authority store. Dispatch owns correlation/progress; the Workspace association owner owns reservation/history; B1 owns proposal/ACK acceptance. Persist authenticated versioned records with fsynced atomic replacement and directory sync before returning durable success. This is forward recovery across independently durable participants, not a claim that two atomic file writes are jointly atomic.

Use a per-key lock/CAS for first correlation and generation changes, a per-World association lock for reserve/move/close, and B1's existing persistence lock for proposals. Do not nest participant locks: perform one owner operation, release its lock, then CAS its authenticated readback into the correlation. No global authority lock is held across network/process I/O. Participant calls bind fixed correlation/request/proposal/destination plus expected coordinator generation. Persist reverse correlation mappings at both association and B1 so either half of an interrupted join is discoverable. Idempotent replay returns only original immutable material; generation/closed-state mismatch cannot allocate substitutes.

`bind_or_read_request` fixes one execution actor and B1 request identity before prepare. `reserve_world_association` fixes the exact association revision; `reserve_consumer_proposal` invokes existing B1 identity allocation with that fixed request. A complete pre-send record exact-joins both authenticated results, original material seal, E1/E2 inputs, delegation and backend custody. Read them back before `MaySend`. Missing/conflicting evidence remains Preparing or explicit integrity failure; it never authorizes a send. Same-key duplicates use the original reservation even after a later permitted move; new keys validate the current association.

**Close-before-effective-commit rule:** an applicable policy/delegation/source/disclosure/current-use/destination/custody invalidator first records durable intent and denies new local permits, closes/fences the older service gate, obtains its durable ACK, **then** commits the authoritative effect-facing change where that ordering is needed. An already-effective revocation cannot be postponed merely by delaying its response. Every applicable invalidator must participate, or this profile is unsupported/design-only. This target mechanism preserves immediate-at-authoritative-commit semantics; it does not require a stronger distributed transaction by default. A concrete owner requiring an incompatible earlier effective event needs an explicit source/event/counterexample and authority disposition before dependent implementation.

**Service gate:** proposed `crates/world-service/src/consumer_admission.rs::TaskAdmissionGate` journals one monotonic epoch per exact Workspace/World/backend and attempt facts under an authenticated owner-enrolled channel. `Open(epoch, owner_revision_vector, service_incarnation)` is allowed only after positive current owner evidence and startup handshake. Client/owner assertions, timestamps, expired leases and strict parsing alone are insufficient. The carrier binds authority store, principal/delegation, actor/session/backend, original proposal/reservation/material seal, epoch, incarnation, coordinator generation and attempt ID. Generic execute must reject this consumer family without its validated carrier; no downgrade fallback bypasses the gate.

| Proposed service operation | Durable linearization and result |
| --- | --- |
| `open_admission_epoch` | Validate positive current owner revisions and service incarnation; open only a fresh epoch. A closed old epoch is never reopened. Unsupported H3/current-use or custody evidence refuses. |
| `consume_task_attempt` | Under only the exact gate/attempt journal lock, validate authenticated owner/channel, open epoch/current revision vector, incarnation, generation and complete original joins; durably record one `Consumed` before releasing to the existing producer. Duplicate consume returns original evidence and never starts the producer again. |
| `close_admission_epoch` | Serialize against consume in the same journal, close forever and ACK its original close ID. Close-first rejects delayed send; consume-first preserves admitted evidence. Effective invalidation commit follows recovered close ACK, with local permits denied throughout ACK uncertainty. |
| `fence_task_attempt` | Atomically record durable `NeverConsumed` even if no packet was seen, or return original `Consumed`/producer evidence. Tombstone rejects delayed packets forever; absence alone cannot prove no future send. |
| `read_task_attempt` | Non-mutating exact read of authenticated attempt/epoch/fence and retained original producer evidence; no execute/reopen/cleanup. Unreadable journal is unavailable/integrity, never empty. |

Before any transport call can escape, dispatch durably CASes and syncs `MaySend(attempt_id, epoch, incarnation, generation, original_proposal, reservation, seal)` and verifies readback. This conservatively exposes `SubmissionUnresolved` even after a crash that sent no bytes. Runtime consume is the ordered **effect-admission point**, not B0 Start, B1 acceptance, task terminality or B04 delivery. Consume can win before a close; subsequent emergency invalidation/cancellation follows its existing owner. A persisted old permit alone never authorizes a delayed sender.

Handbook's exact retained-material grant must positively specify permitted use/scope/lifetime. Version-stable material does not evade a newest-source rule. If currentness depends on latest source/disclosure state, its authoritative invalidators close the old gate before effective commit; a consumer mutex cannot freeze arbitrary Handbook writers. Ordinary source drift must still be validated under the owner's guarded source rules. Unsupported observation/invalidation coverage keeps that route design-only. At actual material delivery, revalidate the separate current-use/delivery authorization required by H3/S1; admission does not pre-authorize a later disclosure or continued use.

On restart the service begins closed for a new incarnation and preserves old attempt tombstones/consumption/original-ACK evidence. Host recovery closes any older live epoch before handshaking current revisions. An unknown service state or missing authenticated journal rejects new effects. Coordinator replacement CASes generation and fences the old attempt; it cannot rely on process death/lease expiry. A crash after durable consume but before producer entry remains unresolved and **cannot** be filled by executing again. The journal retains exact original B0 Start bytes when available for ACK recovery; `Consumed` alone cannot manufacture acceptance.

### 4.9 Durable request join and recovery candidate

**One accountable recovery composition:** WorldDispatchControl's proposed `recover_consumer_admission` is explicitly activated at trusted host startup or an authorized system/operator recovery action. It uses original correlation/proposal/attempt/reservation/material custody and authenticated participant readbacks, with per-record CAS. Reconcile is pure read and cannot activate this writer. Recovery never replays `execute_stream`, selects latest context/current Lane, mints replacement identity or silently repairs historical material.

| Durable state / crash boundary | Authorized transition and exact readback | Custody rule |
| --- | --- | --- |
| Correlation bound, no participant prepared | Current execution authority and explicit unresolved-custody permission permit original idempotent prepare calls. A finite-only retention grant that can expire before positive resolution makes the profile unsupported/refused before possible send; denial closes original generation and obtains attempt fence before any recorded refusal requiring it. | Key/actor/request mapping fixed; no partial send or assumption of permission renewal. |
| Association reserved but B1 absent, or B1 present but reservation absent | Read reverse correlation from both owners; complete the **same** join or close it through positive fence and participant close ACKs. Missing counterpart alone proves nothing about delayed writers. | Original reservation/proposal retained; no substitute allocation. |
| All joins complete, current policy/delegation/source/destination/custody invalid | CAS correlation closed, fence service attempt, then `close_unsubmitted_proposal`/`close_reservation`; record exact ACKs. Only `NeverConsumed` plus complete close evidence yields `RefusedBeforeSubmission`. | Release only after all no-send participants confirm; immutable refusal/key tombstone remains. |
| `MaySend`, transport error or ACK missing | `SubmissionUnresolved`; exact service attempt/fence, original B1 proposal/ACK and available original producer/supervisor reads. A delayed packet must meet its original epoch/incarnation/generation or be rejected. | Hold all original custody; no second send or timer-based release. |
| `Consumed`, producer entry/Start unknown | Remain unresolved until original authenticated producer/ACK evidence exists. Consume is not Start, and absent Start cannot authorize re-execution. | Retain original admission/association/material/evidence hold under the explicitly required until-resolution custody permission; no fixed cutoff, deletion or implicit renewal while unresolved. Visible unavailable status and operator escalation. |
| Exact B0 ACK recovered | B1 persists only matching original immutable acceptance; B2.1 claims and journals exact stream before later frames bypass it. Missing claim/E2/B2.2/binding remains `AcceptedMaterialIncomplete`. | No acceptance rollback or pre-submission refusal. |
| All original B1/B2.1/E2/B2.2/B03 joins authenticate | Publish complete immutable consumer composition; independently expose current work observation. | Accepted history survives current policy/association changes under present read authorization. |
| Accepted work exact terminal, hold release requested | Supervisor supplies exact terminal identity; `read_custody_close_evidence` and state owner supply separate cleanup/diff/state disposition; association owner `close_reservation` authenticates all refs and records release. | Terminal alone is insufficient; unresolved cleanup/state keeps hold. No Lane-wide barrier or deletion. |
| Returned complete composition later unreadable/corrupt | `ReadFailure` for unavailable/integrity with only safely verified authorized facts. Explicit privileged recovery may repair original joins from owner evidence, never new source resolution. | Preserve known acceptance and custody. Separately authorized completed-history deletion after positive resolution instead yields B01's distinct `ExpiredHistory`; a finite history horizon cannot terminate unresolved custody. |
| UI disconnect, host/service restart or recovery interruption | UI detaches; trusted startup resumes owner recovery. B2.1 uses only exact retained producer replay, which may be unavailable after service restart. | No implicit cancel/terminality, deletion, reassociation or new request. |

Accepted composition exact-joins authority store/session/caller/backend, B1 request/proposal/acceptance/task identity, B0 stream/acceptance sequence, B2.1 claim, original immutable E2 bytes/refs, B2.2 receipt, original B03 reservation/binding and B04 material seal. The association owner publishes the reserved historical destination only after matching B1 acceptance; current association is never a substitute. Authenticated but inconsistent evidence is an integrity failure, not a reason to reconstruct policy/binding from current state.

No-send close uses this order: CAS the correlation generation closed to preparation; durably fence the original attempt; read `NeverConsumed` or retain the actual consumed outcome; obtain B1/association/material participant close evidence; finally release the association hold. A stale prepare can at most leave another inert original record; it cannot reopen the closed generation or bypass service tombstones. Recovery of already-admitted evidence does not reuse revoked authority for new effects. Resuming genuinely pre-submission preparation still needs all current owner checks and the same original identities; no attempt is regenerated after `MaySend`.

There is no promise of eventual resolution when runtime evidence is unavailable. Before admission, B01 §3.3 therefore requires explicit owner permission covering original material and recovery-evidence custody until positive resolution, with no cutoff that can expire while unresolved. If an owner offers only an incompatible finite grant, refuse that profile before possible send; recovery cannot assume renewal, extend permission, delete original custody or re-execute/re-resolve. Positive resolution means conclusive original no-send close with participant hold disposition, or exact original accepted-work terminal plus state/custody close evidence; complete acceptance alone is insufficient. Only then may a separately permitted completed-history horizon/deletion policy apply. Custody permission is not permission to access/disclose/use sources or deliver material after revocation; existing source/use fencing and later delivery/current-use guards remain. Expose last recovery status, exact unresolved boundary and authorized operator escalation; timeout/admin action cannot certify no work. [B01 §3.3](collider-b01-b05-handoff.md#33-consumer-boundary-candidate-and-failure-mapping--2026-09-21) fixes privacy, tombstones, non-mutating read and retention constraints. The first proof disables consumer reassociation/replacement/promotion while in-flight/nonterminal or cleanup/state-unresolved. Broader migration remains separately scoped; this protocol does not choose a scheduler, backing store, merge engine or filesystem model.

## 5. Stateful operations: required distinctions, not implemented APIs

| Operation                    | Required accounting                                                                                                                                                           | Not implied                                                                               |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Runtime restart/recovery     | Exact retained state/identity and pending-work recovery disposition.                                                                                                          | State deletion, successful recovery, or a new Lane.                                       |
| World replacement            | Old and successor realization references; custody of base/diffs; explicit unfinished-work and cleanup disposition.                                                            | Discarding the predecessor or using generation as sibling identity.                       |
| World reassociation          | Source/destination Lanes, expected association revision, destination authorization/baseline, override reconciliation, active and in-flight work disposition, durable history. | Copying or merging content, authority widening, or rewriting old receipts.                |
| Change promotion/integration | Exact source changes/base and destination state, applicable gate, conflict check, result and failure/recovery evidence.                                                       | Moving the source World, terminating siblings, or atomic rollback not actually supported. |
| Optional propagation         | Explicit source revision/change selection and recipient Worlds; each recipient's authorization and conflicts.                                                                 | Mandatory catch-up or declaring all unsynchronized Worlds invalid.                        |

**Bounded proof recommendation:** keep World association fixed while the selected ephemeral work is in flight or nonterminal. Disable consumer-driven reassociation/replacement/promotion in that proof. This is not a permanent ban on active-work transitions in the complete architecture; it prevents the first proof from depending on an undesigned migration protocol.

For a later transition implementation, specify prepare/authorize, freeze or reconcile relevant work, commit association/state custody, and recover uncertain outcomes. These are required concerns, not a ratified state machine. A failed or interrupted operation must report which effects are known versus uncertain; it cannot erase pending diffs or claim that a move performed a merge.

### Alternatives and recommendation boundary

| Alternative                                                            | Disposition / tradeoff                                                                                                                                                                                                        |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace association authority + delegated exact-World resolution     | **Recommended:** fits one coordinator/many Worlds without changing its session identity. Requires explicit policy, admission and physical-custody owner changes—not an exposure-only adapter.                                 |
| Use already-existing exact sessions with explicit delegation           | Useful bounded proof or supported special case. It does not establish durable Lane ownership or arbitrary multi-World dispatch; authorization and custody must still join.                                                    |
| Create a hidden orchestration session per World                        | Not recommended as the general model: introduces artificial caller/lifecycle identities and extra ownership/coordination solely to satisfy existing equality checks. Real independently requested sessions remain legitimate. |
| Replace the session's one World with a list                            | Not recommended: broader HSA, adoption and policy changes, yet still conflates session relationships with durable Lane/World authority. A list alone supplies no delegation or race protection.                               |
| Temporarily rebind the orchestrator session or disable steering checks | Reject: races with other work, changes authority behind existing callers, and cannot satisfy remaining exact owner checks safely.                                                                                             |

The 2026-10-21 joint design in §§4.6–4.9 refines these historical recommendations into concrete proposed authorization, storage, transaction, fencing and exact-session custody interfaces. It authorizes no runtime implementation and claims no component-owner signoff. General selected-World custody, Lane-orchestrator delivery and filesystem/environment mechanisms remain separately open; they are not prerequisites to this bounded exact-session design.

### Semantic decisions that can proceed independently of mechanism research

Proposed review disposition: Lane identity/association authority is Workspace-scoped; session authority, accepted work, worker lifecycle, and physical realization retain separate owners. Current association changes are revision-checked, while accepted-work attribution is immutable and separately readable under current authorization. A stale destination is refused or reconciled, never silently retargeted. Names, directory paths, Git branches, image IDs, and runtime liveness cannot substitute for these references.

These identity rules are independent of filesystem realization; §§4.7–4.9 now select the bounded admission persistence/module responsibilities. The [research brief](../../ideas/world-state-environment-research.md#relationship-to-b01b05) instead gates selection and proof of project/environment isolation and stateful transition mechanisms. Older guest-rootfs plans remain inputs with a separate delivery decision; they are not automatically adopted or placed into the future alternative-Lane-backing category. No mechanism experiment has been dispatched.

## 8. B03 acceptance cases and remaining design decisions

Required tests for later implementation (not executed here):

| Case                                                                                 | Required observable result                                                                                                                                                                            |
| ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Two Worlds in one Lane, multiple workers in a World                                  | Distinct exact destinations and work identities; no forced one-to-one alias.                                                                                                                          |
| Missing/ambiguous World; forged or cross-Workspace association                       | No launch/acceptance; explicit authorized error without leaking forbidden identities.                                                                                                                 |
| Association changes after validation but before submission                           | Serialized resolution or conflict; no work accepted against an unvalidated destination.                                                                                                               |
| Submission ACK lost while a transition is attempted                                  | Same-work reconciliation; no second launch and no unaccounted association move.                                                                                                                       |
| World association moves A→B→A; a new request submits old A revision                  | Stale association refusal before any launch; equality of the Lane ID does not revive the selector. An already accepted request instead returns its original binding under current read authorization. |
| Unrelated sibling joins or Lane display name changes                                 | Selected World binding remains usable if its own revision and all other admission checks still hold.                                                                                                  |
| B1 accepted, but receipt/binding composition is incomplete                           | Recoverable request remains linked to original work; no complete consumer acceptance or false no-work refusal.                                                                                        |
| HSA bound World differs from selected destination on the existing exact-session path | Refuse that path; no silent HSA rebind or client-fabricated delegation. A future composite path requires independently validated selected-World authority, not relaxed equality checks on this path.  |
| Authorized Workspace and Lane callers select one World                               | Distinct authentic initiators, one stable physical custody context; Lane caller cannot use a sibling Lane's association, and no session/caller field is spoofed.                                      |
| Crash between association reservation and B1 proposal/link publication               | Recover only the original correlation; no launch before a complete join and no assumption that a missing counterpart proves safe abandonment.                                                         |
| Actor/delegation revoked after preparation; accepted history read later              | Fresh effects obey revocation/launch ordering; historical read separately enforces current access without reconstructing the accepted policy or relabeling work.                                      |
| Work accepted in A; World later moves to B                                           | Historical binding remains A; current association is separately B; current read/action authorization still applies.                                                                                   |
| UI closes, host episode parks, or one worker finishes                                | No implicit Lane/world deletion or fabricated completion of unrelated work.                                                                                                                           |
| One World promotes while siblings continue                                           | Gate applies to selected work; optional updates do not force a Lane-wide barrier.                                                                                                                     |
| World replacement or interrupted merge                                               | Diffs and partial/uncertain effects remain accounted for; no unsupported rollback/success claim.                                                                                                      |

The 2026-10-21 design selects concrete module/store responsibility, actor/delegation checks, authenticated original joins, cross-owner recovery and runtime close/consume ordering for a narrow later implementation assignment. New versioned wire/storage schemas and exact capability/error encodings are engineering implementation work within that contract; general Lane pagination and broader selected-World custody are outside the first route. Real-profile admission still requires B01 §3.4’s positive manifest/handshake and actual applicable owner support; current support is unqualified, not presumed. Independent review of these exact documentation bytes, actual implementation authorization and installed proof remain separate. No plural HSA binding, broader Lane backing or promotion mechanism is selected.

**Review exit:** every proposed rule is accepted or amended by its relevant owner, the consumer can identify an exact historical execution binding, and unsupported broader operations are explicit. Runtime readiness additionally requires actual authenticated access and the relevant installed-path tests. This draft satisfies neither exit by its existence alone.
