# B03 proposal: Lane, World association, and accepted-work binding

**Status:** Draft for owner-contract review, 2026-09-20. Not an accepted API, canonical-owner replacement, implementation dispatch, or runtime-readiness claim.
**Purpose:** Make the confirmed multi-World Lane model precise enough for Collider to display and control one exact accepted task without guessing its execution destination.
**Companion:** [B01–B05 handoff](collider-b01-b05-handoff.md), including evidence pins, shared boundaries, and remaining decisions.
**Intent source:** [Core architecture dossier](../../../SUBSTRATE_CORE_ARCHITECTURE_SESSION_DECISIONS_2026-09-20.md), especially SCA-02–05 and SCA-07–12. The dossier retains confirmed intent; this file proposes its contract expression.

**Planning checkpoint, 2026-09-21:** B03's target behavior is ready for review as part of the [bounded B01–B05 planning handoff](collider-b01-b05-handoff.md#91-planning-handoff-disposition). Collider selects an existing owner-backed association, retains the exact returned references, and displays historical binding separately from current association. It does not create/move/promote Worlds through this bounded consumer surface. Concrete storage/fencing/custody mechanisms and runtime proof remain implementation gates, not prerequisites to planning against these semantics. This checkpoint does not approve the new owner contract or declare it callable.

## 1. Scope and authority

The narrow consumer needs Lane/World selection by an authenticated caller, authorization for the requested operation, a validated association, immutable execution provenance, and an authorized read of that provenance. It does not need a merge engine, automatic routing, remote backing, or an always-running lane orchestrator.

This proposal does not add fields to an existing V1 record. Operation labels and semantic field lists below are design vocabulary, not callable APIs or selected serialization. Existing strict decoding, reference validation, and owner boundaries remain controlling until explicitly amended.

The current [authority map](../../../llm-last-mile/runtime-refactor/architecture/authority-map.md) assigns session identity and session-to-World binding authority to HSA, physical realization to the runtime/backend, acceptance to the Receipt Registry, observation/terminal truth to the Supervisor, and worker lifecycle to RetainedWorkerRuntime. None becomes a second Lane scheduler through this proposal.

**Recommended ownership:** establish a Workspace-scoped Lane-association authority in the shell/agent-runtime authority layer, reusing trusted persistence capabilities rather than creating another service or scheduler. It owns Lane identity, current World association, association history, and association-admission reservations. HSA retains session identity/posture/continuity; backend/runtime owners retain physical World custody. Module names, storage schemas and cross-owner transactions require owner review. This is a new logical responsibility, not a claim that HSA already owns multi-World Lane state. The source-backed recommendation and required changes are below.

## 3. Proposed identity and reference model

Keep these meanings distinct even if an implementation can store some together:

| Identity/reference              | Meaning and owner                                                                                                                                                      |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace reference             | Authorized Workspace identity; not a directory string supplied as authority.                                                                                           |
| Lane reference                  | Stable identity within its Workspace. A display name is not an authorization token.                                                                                    |
| World realization reference     | Exact backend World identity and generation/realization discriminator validated by existing World owners. Do not repurpose generation to mean a sibling World or Lane. |
| Association reference/revision  | Owner-issued evidence that this World is associated with this Lane at a specified revision. Changes create history, not retroactive relabeling.                        |
| Work/acceptance reference       | Exact accepted task/turn identity from the existing acceptance owner; not a Lane, worker, provider session, or UI segment ID.                                          |
| Orchestration/worker references | Coordinator and worker identities, separately authorized for their roles. Their lifetime does not define Lane lifetime.                                                |
| Configuration provenance        | References to baseline, explicit overrides, effective desired configuration, and applied environment evidence; not one interchangeable hash or permission grant.       |

References are opaque and owner-validated. Reuse existing exact ref and store conventions where applicable; do not expose private leases, credentials, resume handles, or internal capabilities to Collider. Whether a World can be unassociated before admission remains outside this proposal's selected path, which requires an existing associated World.

### 3.1 Review candidate: separate membership, association, and acceptance revisions

Use an owner-qualified Workspace/Lane reference and an exact backend World reference. A bare `world_id` is insufficient outside its owning scope; preserve the existing store/backend/world/generation qualification wherever the owner requires it. Restoring or copying storage must not silently mint a second authority for the same references.

Recommended semantic shapes (not serialized records or new public type names):

```text
DestinationExpectation = {
  workspace_ref, lane_ref, exact_world_ref, expected_world_association_revision
}
AcceptedBinding = {
  exact_acceptance_ref, destination_at_acceptance
}
```

`destination_at_acceptance` contains the same four identity/revision meanings as `DestinationExpectation`, validated by owners rather than copied from the client. `exact_acceptance_ref` retains the existing authority-store/acceptance-record/revision qualification; the authenticated join resolves the exact task/run, request, session, and caller. Names here do not replace the existing ref schemas.

- **Lane membership revision** identifies the association-list cut; adding an unrelated sibling World may change it.
- **World association revision** identifies this World's current Lane association. A move A→B→A must not make the old A selector valid again. Reject stale revisions even when names/IDs appear unchanged. Numeric encoding and revision allocation remain open.
- **Acceptance/observation revisions** belong to the existing work owners, not either association revision. A new observation or renamed Lane does not rewrite `AcceptedBinding`.

Bind admission to the selected World's association revision, not a Lane-wide display revision. This avoids rejecting unrelated work merely because another World joined the Lane. Separately validate current policy/configuration requirements; an unchanged association revision is not proof that they remain valid. List-cursor invalidation and admission validity are different decisions.

## 4. Proposed operation semantics

### 4.1 Read a Lane and its associated Worlds

**Input:** authenticated caller, Workspace/Lane reference, optional continuation cursor.
**Success:** Lane-owned facts at an identified association revision; authorized associated World references; separately sourced observations and their freshness/completeness. Lists use owner-scoped cursors and an explicit end/continuation indicator.
**Failure:** denied, unknown target, stale cursor, unavailable owner, unsupported operation/version, or invalid reference. Unauthorized callers must not receive hidden World identities through errors or lists.

This read is not a global Workspace snapshot. A coherent association listing does not imply all worker, diff, policy, or readiness projections share one atomic cut. Partial observations remain explicitly partial.

### 4.2 Validate a concrete execution destination

**Input:** authenticated caller/delegation, Workspace, Lane, exact World realization, expected association revision, requested operation, and relevant configuration/context expectations.
**Checks:** same Workspace; current exact association; authorized caller and operation; matching realization; current applicable policy; required capability/readiness; configuration/context preconditions.
**Success:** owner-validated binding evidence for the submission boundary. It is not acceptance, a permanent authorization grant, or permission to skip launch-time validation.

For the first proof, require an explicit existing World selection. A Lane-only request with several Worlds is not executable work until an authorized coordinator selects a concrete destination. Reject absent/ambiguous selection rather than choose an arbitrary World or create one silently. An orchestration message may target a Lane to request planning; it is not yet B01 World-work acceptance.

Proposed public failure meanings include missing destination, association changed, wrong Workspace/Lane, realization mismatch, policy denied, unsupported capability, readiness unavailable, and owner unavailable. Exact serialized variants and privacy-preserving mappings remain owner design work.

### 4.3 Bind accepted work without a race

1. Resolve the concrete destination and capture its association revision before a possible launch effect.
2. The association authority and dispatch/admission owners establish a revision-bound reservation or equivalent serialized protocol. A check followed by an unguarded launch is insufficient.
3. Keep the selected association stable through runtime submission and uncertain acknowledgement. A transition cannot evade an in-flight admission merely because it has not produced a receipt yet.
4. Only existing runtime acknowledgement and acceptance owners can establish accepted work. Bind its immutable provenance to the exact Workspace, Lane, World realization, association revision, and applicable accepted policy/configuration references.
5. Publish a consumer acceptance result only after its required receipt, supervision, policy, and binding joins are durable and recoverable. If reporting fails after runtime acceptance, reconcile the same work; do not launch another task.

The candidate protocol deliberately avoids prescribing a new lock or record format. The responsible owners must specify the reservation, crash boundaries, and release conditions before implementation. An unknown submission remains unresolved; it is not safe evidence for releasing state custody or changing the selected destination.

**Preserve acceptance ownership:** B03 evidence neither manufactures acceptance nor changes the immutable acceptance owner's meaning. The receipt owner must choose an explicit versioned carrier or authenticated linked projection; never append unrecognized fields to a frozen V1 schema.

### 4.4 Read historical binding

Read accepted binding by exact work/receipt reference under current caller authorization. Return the association at execution acceptance, separately from any current World association. If World W moves from Lane A to Lane B, work accepted in A remains attributed to A. Authorized views may show the move separately; they must not relabel old work as executed in B.

Historical provenance does not grant present action authority. Cancellation/inspection continues through exact accepted-work owners; never substitute the World's current Lane or newest run for the original target. If a transition makes a live route unavailable, expose that condition rather than inventing terminality or redirecting cancellation to different work.

### 4.5 Proposed receipt composition and the HSA bridge

**Recommended carrier:** return a versioned consumer composition containing the existing authenticated receipt projection plus an authenticated `AcceptedBinding` projection. Keep the B03 relationship with its Workspace association owner and join it to the existing exact B1 acceptance reference; do not add Lane fields to frozen receipt V1, copy acceptance into a second registry, or expose the private E2-RM witness. Storage layout and the transaction/recovery protocol remain owner decisions.

The binding may be prepared against a proposed acceptance ID before launch, but it is not an accepted binding until joined to actual B1 acceptance. Runtime acceptance can precede completion of this consumer composition. If any required join is missing or conflicting, return the recoverable B01 request disposition, not a fabricated complete receipt or a refusal implying nothing launched. [B01's outcome table](collider-b01-b05-handoff.md#31-request-admission-and-consumer-acceptance-are-separate) governs that distinction. A conflicting durable join needs owner recovery; it is never repaired by reading the World's current Lane.

**Source-backed disposition:** current exact-session dispatch is reusable only when its canonical caller and bound World already match the request. It cannot directly express a Workspace orchestrator dispatching into a different selected World: the source resolver unconditionally enforces caller/session/World equality before launch. The additional physical session-ownership constraint also matters for retained/member execution. These are specific extension points, not evidence that every HSA schema must change or that singular session binding should become a list. §7 records the inspected paths.

### 4.6 Recommended model: authorized selection, not session rebinding

**Recommend:** keep orchestration identity and session binding intact; add owner-authenticated selected-World resolution at the dispatch boundary. It composes four distinct inputs:

1. **Initiator:** authenticated human or delegated principal and requested operation. For agent-originated work, HSA resolves the exact current session and its canonical caller; it does not authenticate an arbitrary external principal. Ingress must separately authorize that principal/delegation. A parked episode or available receipt is not permission to act.
2. **Destination:** Workspace/Lane/exact World plus expected association revision, validated by the Lane-association owner. Workspace references must resolve an enrolled Workspace and its trusted root; an authority-store ID alone is not a Workspace ID, and a supplied path is not authority.
3. **Execution/custody authority:** the existing runtime/backend's exact World owner or a successor mapping authorized by that custody owner, not self-approved by dispatch. The acting Workspace or Lane orchestrator is an authorized user of that destination, not automatically its physical owner. Reassociation changes neither custody nor historical acceptance by implication.
4. **Constraints:** current actor/delegation, Workspace and applicable Lane/World restrictions are resolved through policy owners; E1/E2 supply the exact admitted material. Do not merely copy the host session's policy to another World. Existing immutable worker-cap narrowing remains controlling; no new grant can widen it through a turn patch.

**Delegation responsibility (proposed allocation for architectural approval):** trusted Substrate-facing ingress establishes the real initiating principal; HSA independently resolves agent-session/canonical-caller facts. Substrate's policy/authorization owners decide whether that actor, through the claimed delegation, may request the exact operation against the selected resource and execution context. WorldDispatchControl owns the admission check that obtains and enforces that decision before permitting effects; it must not grant delegation to itself or treat a caller-supplied selector as approval. Lane-association authority validates membership/revision, not permission to act. Coordinator status, Lane attachment, a request ID, or possession of an execution-context reference grants no authority. Workspace/Lane scope is validated, not selected as a privilege mode by the caller.

This allocates logical responsibilities, not an implemented delegation API or a new authorization service. On 2026-09-21 the user authorized proceeding with the joint B01/B03 design pass using this direction; that is not canonical-owner approval or implementation admission. The candidate owner interfaces below refine the direction, including denial and revocation behavior. Current authorization for historical reads remains separate from permission to cause new effects.

The result is an owner-produced, request-bound admission witness, not client-supplied permission or a reusable broad bearer token. It joins the real initiator, exact HSA caller where applicable, destination revision, execution/custody authority, and owner policy/configuration references. Constructing that witness records the validated owner decisions; it does not acquire or replace their authority. The first implementation may keep this as a typed internal value plus durable correlation; no new public token format, signature scheme, schema version, or crate is selected here.

Workspace orchestration can request any authorized association in its Workspace; a Lane orchestrator can request only its authorized Lane scope. Both use the same dispatch resolver. Direct Workspace intervention retains its real initiator and coordinator-visible causation; it does not impersonate a Lane agent. For a worker created by another coordinator, original worker/acceptance/cap identity remains fixed; authorization of a new controlling actor is a separate check, not a rewrite of the creator.

HSA session records need not gain a plural World field for this design. New dispatch resolution must accept the composite witness instead of using the caller session's World field as the sole destination authority. HSA still supplies authenticated session facts and trusted storage access; exact stored-schema changes, if needed, require their own explicit owner amendment. A host-bound session with no bound World is not by itself an executable grant.

For the **bounded first proof**, require an eligible existing session/caller whose World already matches, plus genuine owner-backed Lane association and authenticated consumer ingress. A human request must not fabricate an orchestrator caller to enter that route; if no approved delegation exists, the request remains unadmitted. This proves only that selected path. Full multi-World dispatch and cross-coordinator retained control require the composite resolver and physical-owner reconciliation, even if the first proof succeeds. B01's runtime-profile gate applies to both.

### 4.7 Association/admission consistency and recovery

Recommended ordering: authorize request access → resolve an existing request before any fresh dispatch → validate a new destination and reserve its association → join the exact B1 proposal and policy inputs → revalidate/seal admission at the effect boundary → submit → join B1 ACK, B2.1/E2/B2.2 and immutable B03 binding. The initiator-to-execution mapping is fixed for this request; retry never selects a different current orchestrator or World to get past a failed join.

The association owner and B1 must implement a durable cross-owner join protocol before this can run. Reuse trusted lock/transaction capabilities, but do not assume two independently atomic writes are jointly atomic, or hold a global authority lock while awaiting runtime I/O. Reserve the selected World's association revision, not all Lane membership; unrelated sibling changes need not invalidate it. Serialize association mutation against admission, and define the policy owner's revocation/launch ordering separately—an association reservation cannot freeze revoked permission.

| Interruption boundary                                          | Required recovery; no inference from absence alone                                                                                                                                                                                                                                 |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Association reserved; B1 proposal not yet durably joined       | No submission allowed. Recover the original correlation and establish exact proposal disposition before completing or abandoning this reservation.                                                                                                                                 |
| B1 proposal exists; association join incomplete                | No submission allowed. Recover the same proposal and validate the original reservation; never allocate a new proposal or retarget to make the join succeed.                                                                                                                        |
| Submission may have occurred                                   | Keep association/correlation custody unresolved; only exact runtime/acceptance recovery can advance it. Timeout, lease expiry, UI loss, or a missing receipt cannot release it for reassociation/relaunch.                                                                         |
| B1 accepted; policy/observation/binding composition incomplete | Preserve original accepted work; complete only from owner evidence. Return B01's accepted-material-incomplete disposition, never no-work refusal or a fabricated binding.                                                                                                          |
| Complete acceptance or conclusive pre-submission refusal       | Preserve immutable history. Refusal releases the reservation only after all participants exclude a pending/possible submission. In the first proof, accepted work continues to block reassociation until exact terminal evidence and separate state/custody checks permit release. |

These records describe association reservation and join progress, not a second task lifecycle. The Supervisor still owns work terminality; terminal work alone does not prove that World diffs, cleanup, or promotion are resolved. Historical reads require current read authorization but use original binding/policy evidence, even after a permitted move or caller/session change. New work requires a new authorized admission.

**Actor mapping rule:** a human may request work through a specifically authorized executing agent/session without losing the human's initiating identity. An agent caller must match HSA's canonical actor. A Lane coordinator additionally needs authority over the selected Lane; a Workspace coordinator does not acquire unrestricted authority merely from its role. No approved mapping means no executable submission. Credential rotation can preserve an authenticated principal; changing execution session/caller after request binding cannot be used as an automatic retry strategy. Current authorization to read that request is independent of whether its original actor can still execute.

**Revocation rule:** recommend a policy-owner-ordered admission point. If revocation wins before that point, no new effect is admitted; if admission wins, record the exact admitted evidence and treat subsequent cancellation/invalidation through its separate owner. A timestamp or check in an earlier process cannot establish that order. The runtime/dispatch interface must prevent a delayed or replaced submitter from bypassing it. Association reservation and persisted permit evidence do not freeze permission indefinitely. The concrete fencing/consumption protocol is a blocking engineering gate, not a guarantee provided by current steering checks.

### 4.9 Durable request join and recovery candidate

**Recommended placement:** WorldDispatchControl owns the proposed consumer admission correlation and its recovery coordination, using trusted StateStore persistence beside the existing B1 owner. Lane-association records remain with the Workspace association authority. B1, Supervisor and E2 retain their own truth. The correlation stores links and admission progress, not a copied receipt registry or a second execution lifecycle. This is a new bounded dispatch responsibility requiring an explicit owner amendment; it is not a claim that generic StateStore writes or today's dispatch already implement it.

The protected correlation binds: the principal/Workspace/operation/client-key namespace; protected semantic equality commitment; real initiator and fixed execution actor; destination expectation; original B1 request/proposal reference; association reservation; authorization/custody references; and admission revision plus submission/composition progress. Protect equality through owner-approved authenticated storage and commitment rules; do not persist a new prompt preimage, credential, bearer permit, or raw secret-derived digest. Existing B1/E2 records retain their own schemas and privacy rules. Exact storage layout, key/commitment lifecycle, retention and versioned reference encodings remain explicit design gates.

Recommended recovery protocol, refining §4.7:

1. **Bind once.** Serialize first creation of the consumer-key correlation. Identical contenders join the winning record; conflicting inputs receive `KeyConflict`. Select and persist one execution-actor/B1-request mapping before proposal creation. Association reservation and B1 proposal each use that original correlation idempotently; interrupted joins must be rediscoverable from both owners. A missing counterpart in one read is not proof that another writer cannot still publish it.
2. **Join before effects.** Only the authorized dispatch path may advance preparation after the association, proposal, actor, policy and custody joins validate. No complete join means no submission. A short persistence transaction may publish correlation progress, but must not hold a global authority lock across runtime I/O. If owners cannot share a transaction, require exact idempotent owner operations and forward recovery; do not claim rollback of an already published owner record.
3. **Record possible submission before sending.** Durably mark the original attempt as potentially submitted before any runtime send can escape. This can conservatively yield `SubmissionUnresolved` after a crash even when no bytes were sent. Recovery must fence obsolete submitters before allowing any disposition that assumes they cannot send later. A lease timeout or new coordinator process does not provide that fence.
4. **Recover evidence, not an execution retry.** After possible submission, an authorized recovery path queries/consumes exact runtime/B1 evidence using the original identities. Do not replay `execute_stream` merely because the request key or proposal is unchanged. If the supported runtime cannot resolve the ambiguity, retain it as unresolved with association custody held. Any future resubmission protocol requires explicit runtime deduplication/fencing proof; none is assumed here.
5. **Complete original joins.** Once B1 acceptance is known, preserve it and complete missing Supervisor/E2/B2.2/B03 links only from original owner evidence. The association owner records the reserved historical destination, never current association as a substitute. Conflicting or unavailable evidence remains an explicit recovery/integrity failure, not a new launch or automatic rewrite. Consumer reconciliation remains read-only.
6. **Release only with positive evidence.** Pre-submission refusal can release a reservation only after all possible submitters are fenced and owners conclusively exclude a past or future submission for that attempt. Otherwise retain uncertainty. Accepted work follows the first-proof terminal-plus-state/custody release rule in §4.7; no timeout deletes history or permits reassociation.

Recovery coordination is separately authorized system work, not implicit delegation from a UI read. It may repair evidence for already admitted effects without reusing revoked permission for new work. Resuming a definitively pre-submission preparation still needs current execution authorization. Restart entrypoints must invoke owner recovery explicitly; a browser reconnect must not become an alternate repair writer.

**Supported-path gate:** the first proof need not implement arbitrary reassociation or general multi-World dispatch, but must implement the exact selected route's request joins, fencing and honest unresolved outcomes. Unbounded waiting is not a recovery SLA: unavailable resolution must be visible, and retention/operational escalation must be specified before production exposure. This proposal does not claim eventual resolution when the runtime has no authoritative recovery evidence.

## 5. Stateful operations: required distinctions, not implemented APIs

| Operation                    | Required accounting                                                                                                                                                           | Not implied                                                                               |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Runtime restart/recovery     | Exact retained state/identity and pending-work recovery disposition.                                                                                                          | State deletion, successful recovery, or a new Lane.                                       |
| World replacement            | Old and successor realization references; custody of base/diffs; explicit unfinished-work and cleanup disposition.                                                            | Discarding the predecessor or using generation as sibling identity.                       |
| World reassociation          | Source/destination Lanes, expected association revision, destination authorization/baseline, override reconciliation, active and in-flight work disposition, durable history. | Copying or merging content, authority widening, or rewriting old receipts.                |
| Change promotion/integration | Exact source changes/base and destination state, applicable gate, conflict check, result and failure/recovery evidence.                                                       | Moving the source World, terminating siblings, or atomic rollback not actually supported. |
| Optional propagation         | Explicit source revision/change selection and recipient Worlds; each recipient's authorization and conflicts.                                                                 | Mandatory catch-up or declaring all unsynchronized Worlds invalid.                        |

**Bounded proof recommendation:** keep World association fixed while the selected ephemeral work is in flight or nonterminal. Disable consumer-driven reassociation/replacement/promotion in that proof. This is not a permanent ban on active-work transitions in the complete architecture; it prevents the first proof from depending on an undesigned migration protocol.

For a later transition implementation, specify prepare/authorize, freeze or reconcile relevant work, commit association/state custody, and recover uncertain outcomes. These are required concerns, not a ratified state machine. A failed or interrupted operation must report which effects are known versus uncertain; it cannot erase pending diffs or claim that a move performed a merge.

### Alternatives and recommendation boundary

| Alternative                                                            | Disposition / tradeoff                                                                                                                                                                                                        |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace association authority + delegated exact-World resolution     | **Recommended:** fits one coordinator/many Worlds without changing its session identity. Requires explicit policy, admission and physical-custody owner changes—not an exposure-only adapter.                                 |
| Use already-existing exact sessions with explicit delegation           | Useful bounded proof or supported special case. It does not establish durable Lane ownership or arbitrary multi-World dispatch; authorization and custody must still join.                                                    |
| Create a hidden orchestration session per World                        | Not recommended as the general model: introduces artificial caller/lifecycle identities and extra ownership/coordination solely to satisfy existing equality checks. Real independently requested sessions remain legitimate. |
| Replace the session's one World with a list                            | Not recommended: broader HSA, adoption and policy changes, yet still conflates session relationships with durable Lane/World authority. A list alone supplies no delegation or race protection.                               |
| Temporarily rebind the orchestrator session or disable steering checks | Reject: races with other work, changes authority behind existing callers, and cannot satisfy remaining exact owner checks safely.                                                                                             |

No additional product-intent question is required by this pass. The user has authorized developing this direction in a joint B01/B03 design pass; canonical-owner approval is still needed before amendments. Exact authorization schema, storage/transaction protocol and backend custody carrier are engineering design gates, not settled implementation. Lane-orchestrator V1 delivery and filesystem/environment mechanisms remain separately open and are not prerequisites to defining this model.

### Semantic decisions that can proceed independently of mechanism research

Proposed review disposition: Lane identity/association authority is Workspace-scoped; session authority, accepted work, worker lifecycle, and physical realization retain separate owners. Current association changes are revision-checked, while accepted-work attribution is immutable and separately readable under current authorization. A stale destination is refused or reconciled, never silently retargeted. Names, directory paths, Git branches, image IDs, and runtime liveness cannot substitute for these references.

These rules can be reviewed without selecting a persistence module or filesystem. The [research brief](../../ideas/world-state-environment-research.md#relationship-to-b01b05) instead gates selection and proof of project/environment isolation and stateful transition mechanisms. Older guest-rootfs plans remain inputs with a separate delivery decision; they are not automatically adopted or placed into the future alternative-Lane-backing category. No mechanism experiment has been dispatched.

## 8. B03 acceptance cases and remaining design decisions

Required tests for later implementation (not executed here):

| Case                                                                                 | Required observable result                                                                                                                                                                            |
| ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Two Worlds in one Lane, multiple workers in a World                                  | Distinct exact destinations and work identities; no forced one-to-one alias.                                                                                                                          |
| Missing/ambiguous World; forged or cross-Workspace association                       | No launch/acceptance; explicit authorized error without leaking forbidden identities.                                                                                                                 |
| Association changes after validation but before submission                           | Serialized resolution or conflict; no work accepted against an unvalidated destination.                                                                                                               |
| Submission ACK lost while a transition is attempted                                  | Same-work reconciliation; no second launch and no unaccounted association move.                                                                                                                       |
| World association moves A→B→A; a new request submits old A revision                  | Stale association refusal before any launch; equality of the Lane ID does not revive the selector. An already accepted request instead returns its original binding under current read authorization. |
| Unrelated sibling joins or Lane display name changes                                 | Selected World binding remains usable if its own revision and all other admission checks still hold.                                                                                                  |
| B1 accepted, but receipt/binding composition is incomplete                           | Recoverable request remains linked to original work; no complete consumer acceptance or false no-work refusal.                                                                                        |
| HSA bound World differs from selected destination on the existing exact-session path | Refuse that path; no silent HSA rebind or client-fabricated delegation. A future composite path requires independently validated selected-World authority, not relaxed equality checks on this path.  |
| Authorized Workspace and Lane callers select one World                               | Distinct authentic initiators, one stable physical custody context; Lane caller cannot use a sibling Lane's association, and no session/caller field is spoofed.                                      |
| Crash between association reservation and B1 proposal/link publication               | Recover only the original correlation; no launch before a complete join and no assumption that a missing counterpart proves safe abandonment.                                                         |
| Actor/delegation revoked after preparation; accepted history read later              | Fresh effects obey revocation/launch ordering; historical read separately enforces current access without reconstructing the accepted policy or relabeling work.                                      |
| Work accepted in A; World later moves to B                                           | Historical binding remains A; current association is separately B; current read/action authorization still applies.                                                                                   |
| UI closes, host episode parks, or one worker finishes                                | No implicit Lane/world deletion or fabricated completion of unrelated work.                                                                                                                           |
| One World promotes while siblings continue                                           | Gate applies to selected work; optional updates do not force a Lane-wide barrier.                                                                                                                     |
| World replacement or interrupted merge                                               | Diffs and partial/uncertain effects remain accounted for; no unsupported rollback/success claim.                                                                                                      |
